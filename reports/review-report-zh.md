# A2A-CDSL 綜合評估報告

**專案：** A2A-CDSL（Agent Compact Domain-Specific Language，代理緊湊領域專用語言）  
**日期：** 2026-10-27  
**狀態：** 設計完成，實作驗證通過，有限範圍內可投入生產  
**測試模型：** Qwen3.8-flash-Next（由 llama.cpp server 在 v100Server 上提供單一模型服務）  

---

## 1. 摘要

A2A-CDSL 是一套專為 AI 代理內部推理與代理間溝通設計的緊湊符號語言。它以單字元代碼和結構化運算元取代冗長的自然語言指令，在多代理任務委派中實現 **65–70% 的 token 削減**。

**結論：CDSL 是有用的**，適用於 token 受限的多代理工作流程。它在輸入 token 和處理速度上帶來可量化的節省。然而，它在生成一致性、錯誤偵測可靠性和生態系成熟度方面存在限制，制約了目前的適用範圍。

## 2. 設計概述

### 2.1 核心架構

```
┌─────────────────────────────────────────────────────┐
│  主控代理（以 CDSL 思考）                            │
│  [THOUGHT]                                          │
│  >sub1:role | ?target | !validation                 │
│  [/THOUGHT]                                         │
└──────────────────────┬──────────────────────────────┘
                       │ CDSL 委派
                       ▼
┌─────────────────────────────────────────────────────┐
│  子代理（解析 CDSL，執行任務）                       │
│  [SUB_RETURN id=sub1]                               │
│  $status:OK | $result:findings                      │
│  [/SUB_RETURN]                                      │
└──────────────────────┬──────────────────────────────┘
                       │ CDSL 結果
                       ▼
┌─────────────────────────────────────────────────────┐
│  人類介面閘道（解壓縮為自然語言）                     │
│  "稽核在 42 個檔案中未發現漏洞。"                     │
└─────────────────────────────────────────────────────┘
```

### 2.2 語言設計

| 元件 | 設計選擇 | 理由 |
|------|---------|------|
| 指令元 | 6 個 ASCII 標點符號（`? > + ! # $`） | 在所有 BPE tokenizer 中為單 token；語義直覺 |
| 語法 | 扁平 pipe 分隔段 | LLM 生成比巢狀 S-expression 更少錯誤 |
| 運算元 | `key:value` 對（key ≤4 字元） | 最小 token 開銷；自我描述 |
| 狀態 | 內容雜湊指標（`#ctx:<hash>`） | 可去重、抗碰撞、4 token vs 內聯 150 token |
| 封裝 | `[THOUGHT]` / `[SUB_RETURN]` 標記 | 將 CDSL 與人類輸出隔離 |
| 擴展性 | 版本化指令元註冊表 | 向後相容的 additions |

### 2.3 三層能力模型

| 層級 | 能力 | 用途 |
|------|------|------|
| 語言 | `cdsl-language` | 語法、指令元、運算元編碼、有效性規則 |
| 協議 | `cdsl-agent-protocol` | 委派、回傳、狀態指標、生命週期 |
| 介面 | `cdsl-human-gateway` | 解壓縮、漸進揭露、保真度 |

### 2.4 關鍵設計決策

| 決策 | 選擇 | 拒絕的替代方案 | 原因 |
|------|------|--------------|------|
| 編碼 | 文字符號式 | 二進位/Base64 | LLM 直接推理文字；無需解碼步驟 |
| 結構 | 扁平 pipe 分隔 | S-expressions（Lisp） | LLM 生成巢狀結構錯誤率更高 |
| 部署 | Prompt 注入技能 | 微調模型 | 跨模型可移植；無訓練成本 |
| 指令元 | ASCII 標點 | 雙字母助記符 | 每指令元 1 token vs 2 token |
| 狀態參照 | 內容雜湊 | 遞增 ID | 可去重、無需協調 |

### 4.4 品質評估

**注意：** 所有測試均使用同一模型（Qwen3.8-flash-Next via llama.cpp）。「第一輪」與「第二輪」之間的差異反映的是 **prompt 品質變化**，而非模型能力差異。

| 測試類型 | 第一輪（基本 prompt） | 第二輪（增強 prompt） |
|---------|---------------------|---------------------|
| 解析 CDSL 輸入 | ✅ 100% | ✅ 100% |
| 生成有效 CDSL | ❌ 0% | ✅ 100% |
| 偵測 CDSL 中的錯誤 | N/A | ✅ 100%（完整保留鍵列表） |
| 複雜 3 代理鏈 | 未測試 | ✅ 完整流水線 |
| 增強迴圈 | 未測試 | ✅ 2 輪 |
| 失敗恢復 | 未測試 | ✅ 定向重委派 |
| 封裝一致性 | ⚠️ 不一致 | ⚠️ 偶爾缺失 |

**關鍵發現：** 模型能力在兩輪之間沒有變化 — 只有 prompt 改變了。增強的技能 prompt（含明確的委派格式規則、完整保留鍵列表、6 個範例）是達到 100% 語法有效性的決定性因素。

### 4.5 損益平衡分析

- 技能/prompt 注入成本：~800 token（一次性，可快取）
- 每次委派節省：~29 token
- **損益平衡點：28 次委派**
- 典型多代理會話：50+ 次委派 → 淨節省 > 600 token

## 5. 評估：CDSL 是否有用？

### 5.1 CDSL 有用的場景

| 使用場景 | 效益 | 證據 |
|---------|------|------|
| 多代理任務委派 | 65–70% 輸入 token 節省 | 所有測試確認 |
| 內部思考鏈 | 更快推理、減少注意力稀釋 | 5× 速度提升 |
| 結構化結果報告 | 一致格式、機器可解析 | 含自我檢查 100% 語法有效性 |
| 代理間狀態共享 | 相比內聯內容減少 97% | 指標式共享運作正常 |
| 錯誤恢復編排 | 緊湊的失敗/重試鏈 | 3 代理流水線含恢復運作正常 |
| 迭代精煉（增強迴圈） | 多輪調查鏈 | 2 輪增強確認可行 |
| 大規模成本降低 | API 成本節省與委派次數成正比 | 每次委派節省 29 token |

### 5.2 CDSL 目前不适用的場景

| 限制 | 影響 | 嚴重度 |
|------|------|--------|
| 生成需要自我檢查 prompt | 若無此機制，語法有效性 0% | 中等 |
| 較小模型的錯誤偵測不可靠 | 對有效表達式產生誤報 | 中等 |
| 無執行期解析器/驗證器 | 無法在執行時強制語法 | 高 |
| 無生態系/工具支援 | 無 IDE 突顯、無 linter、無除錯器 | 中等 |
| 人類學習曲線 | 比自然語言更難除錯 | 低 |
| Prompt 依賴行為 | 品質因 prompt 設計而異，非模型選擇 | 中等 |
| 語言中無條件分支 | 複雜控制流必須留在代理推理中 | 低 |
| 僅單會話狀態 | 無跨會話持久化 | 低 |

### 5.3 總體結論

**CDSL 是有用的且帶來可量化的價值**，適用於：
- 大量委派的多代理編排（每會話 >28 次委派）
- Token 受限環境（小 context window、成本敏感 API）
- 需要一致性的結構化代理溝通

**CDSL 目前尚不成熟於：**
- 單代理工作流程（無委派 = 無節省）
- 需要嚴格執行期驗證的環境（無解析器存在）
- 不熟悉符號 DSL 的團隊（採用摩擦）

## 6. 弱點分析

### 6.1 語言設計弱點

| 弱點 | 描述 | 風險 |
|------|------|------|
| 無條件邏輯 | 無法在 CDSL 中表達 IF/ELSE、迴圈或分支 | 複雜工作流程需要混合 NL+CDSL |
| 無函數組合 | 無法定義可重用的子表達式 | 複雜鏈中產生重複 |
| 僅扁平結構 | 結構化值中巢狀深度僅 1 層 | 限制複雜資料的表達能力 |
| 保留鍵模糊性 | `status`（6 字元）違反 1–4 字元規則 | 混淆模型；需明確列出例外 |
| 無型別系統 | 所有值皆為字串；無型別檢查 | 語義錯誤無聲通過 |
| 無版本協商 | 代理無法協商語言版本 | 混合版本鏈可能失敗 |

### 6.2 實作弱點

| 弱點 | 描述 | 風險 |
|------|------|------|
| 無執行期解析器 | 語法僅存在於 prompt 中；執行時無強制 | 無效 CDSL 無聲地破壞代理溝通 |
| 無驗證工具 | 無法以程式方式 lint/驗證 CDSL 表達式 | 錯誤僅在解譯時才發現 |
| Prompt 依賴品質 | 生成品質完全依賴 prompt 工程 | 模型更新時脆弱 |
| 無錯誤恢復協議 | Stale 偵測已規格化但未實作 | 逾時處理僅為理論 |
| 無安全模型 | 狀態指標無認證/授權 | 代理間潛在內容洩漏 |

### 6.3 測試缺口

| 缺口 | 描述 |
|------|------|
| 無對抗性測試 | 未測試對抗性/模糊的 CDSL 輸入 |
| 無壓力測試 | 未測試 10+ 代理鏈或極長表達式 |
| 無跨模型一致性 | 僅測試 qwen3.8 系列；無 GPT/Claude/Gemini 比較 |
| 無縱向測試 | 未測試多會話狀態持久化 |
| 無人類可用性測試 | 未測試人類除錯/維護體驗 |
| 無安全性測試 | 未測試透過 CDSL 運算元的對抗性注入 |

## 7. 下一階段開發建議

### 7.1 第二階段：執行期強制（優先度：高）

**目標：** 建立輕量級解析器/驗證器，在執行時強制 CDSL 語法。

**交付物：**
- 基於 Regex 或 PEG 的 CDSL 表達式解析器（JavaScript/TypeScript）
- 驗證 API：`validateCDSL(expression) → {valid, errors[]}`
- 代理框架整合鉤子（發送前驗證）
- Pretty-printer：將 CDSL 展開為註解形式供除錯

**原因：** 若無執行期驗證，無效 CDSL 會無聲地破壞代理溝通。這是單一最高影響的改進。

### 7.2 第三階段：擴展語言功能（優先度：中）

**目標：** 新增條件邏輯和組合能力，同時維持 token 效率。

**建議 additions：**
- `@` 指令元用於條件：`@cond:<condition> ?<then> !<else>`
- `~` 指令元用於事件/通知：`~evt:<event_id> | >sub:handler`
- 子表達式參照：`#def:<name> = <expression>` 然後 `#use:<name>`
- 型別註解（選配）：`?f:path:string | !vuln:name:string`

**約束：** 每個 addition 不得增加現有有效表達式的 token 數。

### 7.3 第四階段：生態系工具（優先度：中）

**目標：** CDSL 的開發者體驗。

**交付物：**
- 語法突顯（VS Code 擴充 / tree-sitter 語法）
- CDSL 的 LSP 伺服器（自動完成、懸浮文件、錯誤波浪線）
- CLI 工具：`cdsl validate`、`cdsl pretty-print`、`cdsl benchmark`
- Playground：互動式 CDSL→NL 解壓縮器示範

### 7.4 第五階段：跨模型驗證（優先度：中）

**目標：** 驗證 CDSL 跨模型家族的可用性（目前測試僅涵蓋 Qwen3.8-flash-Next via llama.cpp）。

**測試矩陣：**
- GPT-4o / GPT-4.1
- Claude 3.5 / 4
- Gemini 2.0 / 2.5
- 本地模型（Llama 3, Mistral）

**量測：** 理解準確率、生成有效性、每模型家族的 token 節省。確認 prompt 驅動的可靠性是否能泛化到不同 tokenizer 和模型架構。

### 7.5 第六階段：安全與隔離（優先度：低）

**目標：** 確保 CDSL 狀態指標不會在未授權代理間洩漏內容。

**交付物：**
- `#ctx:<hash>` 指標的存取控制模型
- `[THOUGHT]` 區塊的沙箱邊界
- 狀態存取的審計日誌格式

### 7.6 第七階段：採用與文件（優先度：低）

**目標：** 降低團隊採用門檻。

**交付物：**
- 互動式教學（CDSL 入門）
- 遷移指南：「從自然語言 prompt 到 CDSL」
- 含量化節省的案例研究
- 熱門框架的整合配方（LangGraph、CrewAI、AutoGen）

---

## 8. 結論

A2A-CDSL 是一套**經過驗證、有用的語言**，適用於多代理 token 優化。它達成了設計目標（65–70% token 節省、5× 速度提升、100% 理解準確率），在使用增強技能 prompt 的情況下，可投入委派密集型工作流程的生產環境。

**重要背景：** 所有測試均使用同一模型（Qwen3.8-flash-Next via llama.cpp）。從 0% 到 100% 語法有效性的顯著提升完全是透過 **prompt 設計改進** 達成的 — 而非模型升級。這證實 CDSL 的可靠性取決於 prompt 品質，而這是可控的。

主要風險是**缺乏執行期強制時的脆弱性** — 語言的正確性完全依賴 prompt 工程。最高價值的下一步是建立執行期解析器/驗證器（第二階段），使 CDSL 獨立於 prompt 品質而穩健。

**建議：** 在擴展語言功能之前，先推進第二階段（執行期解析器）。以更多模型家族（GPT、Claude、Gemini）進行驗證，以確認跨模型泛化能力。
